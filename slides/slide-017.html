Harness

Runtime scaffolding that turns a model into an agent that can work.

  • Coordinate model and tool calls.
  • Maintain task context and state.
  • Handle execution boundaries and approvals.

Example: Microsoft Copilot harness in Microsoft Foundry.

A harness is software behavior around the model, not another model or merely compute hosting.
It drives the execution loop, carries context forward, and handles tools and control decisions according to the implementation.
The named example belongs in Microsoft Foundry.

Technical reference, not spoken:
Current Foundry documentation names Microsoft Copilot harness for prompt agents and explicitly labels it public preview.
Studio separately continues to document GitHub Copilot harness, which is not the GitHub Copilot service.
No rename from the Studio name to the Foundry name was established, so no “formerly” history is asserted.
Foundry fixes this harness choice at new-agent creation.
Its preview limits include unsupported BYOM and Foundry Memory, region/tool requirements, and sandbox-managed state rather than unrestricted durable storage.
Foundry manages built-in approval policy during preview, and Shell can independently perform file/network operations when enabled.
The generic foundation is not a guarantee of the same defaults across harnesses.
