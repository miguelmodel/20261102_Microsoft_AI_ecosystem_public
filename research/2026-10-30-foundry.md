## 1. Executive Summary

- **Use Microsoft Foundry as the current platform name.** Microsoft maps the earlier Azure AI Studio / Azure AI Foundry brands to Microsoft Foundry. Foundry brings models, agents, tools, evaluation, and operational capabilities into an Azure-based platform for building custom AI solutions. It is not simply another name for an individual model. [R1] [R2]
- **Customizable/pro-code is a useful emphasis, not an exclusive authoring mode.** Foundry includes visual portal experiences, playgrounds, and declarative prompt-agent configuration, alongside SDKs, editor tooling, and hosted agents running customer code. Avoid describing it as code-only. [R1] [R5] [R6]
- **The customer decision is about the solution and the degree of control required.** Foundry supports adding a model to an application, configuring a managed prompt agent, and deploying custom agent code. Its managed hosting does not remove customer responsibility for application logic, testing, permissions, connected systems, or safe operation. These options do not establish Foundry as a prerequisite for every agent. [R1] [R5] [R6]
- **Availability must be stated by feature.** The current portal is documented as GA for defined core Foundry-project scenarios, but monitoring, agent guardrails, and several other experiences remain preview. Declarative workflows are preview and scheduled to retire on December 1, 2026; they are not a sound new-development recommendation. [R3] [R11] [R17]
- **Combinations are specific, not universal.** Documented examples include publishing supported agents to Microsoft Copilot/Teams, a preview Foundry-agent connection for Copilot Studio's standard harness, and using GitHub Copilot with Foundry development guidance. Each has its own prerequisites and boundaries. [R14] [R15] [R16]

## 2. Current Naming and Key Concepts

### Naming recommendation

| Term | Verified meaning and recommended treatment |
|---|---|
| **Microsoft Foundry** | Current platform name. Use this on first reference and **Foundry** thereafter. Microsoft documents the evolution Azure AI Studio → Azure AI Foundry → Microsoft Foundry. Historical names explain older material; do not present them as separate current platforms. [R1] [R2] |
| **Foundry portal / Foundry (classic) portal** | Different experiences within the evolving platform, not merely interchangeable labels. The current portal focuses on Foundry projects; hub-based projects and some other workflows remain in classic. Do not equate a branding change with automatic workload migration or feature parity. [R2] [R3] |
| **Microsoft Foundry Models** | Model discovery, comparison, evaluation, and deployment capabilities. Azure OpenAI models are part of the offering, alongside Microsoft and other providers' models; Azure OpenAI is not a synonym for the entire Foundry platform. [R4] |
| **Foundry Agent Service** | Microsoft's managed platform for building, deploying, and scaling supported agents. Current documentation distinguishes prompt agents, voice-based prompt agents, and hosted agents. [R5] |
| **Foundry Tools** | Current name for the portfolio previously called Azure AI Services. Distinguish that portfolio name from the broader concept of agent tools, which also includes custom functions, APIs, and MCP servers. [R1] [R2] [R7] |
| **Foundry Control Plane** | Named fleet-management interface for visibility, governance, and control across agents, models, and tools. Do not confuse it with the generic Azure control-plane/data-plane distinction. The migration guide labels this named experience preview. [R2] [R10] [R13] |

### Minimum conceptual model

A model generates or reasons over content; an agent adds instructions and tools that can take actions. Foundry can support either a straightforward model-powered application or a more elaborate agent. The platform overview explicitly offers a single model call as a starting point when tools or orchestration are unnecessary. [R1] [R5]

A Foundry resource provides a top-level management boundary, while projects organize development assets such as agents, files, and evaluations. Connected services such as Storage, Key Vault, and Azure AI Search remain independent Azure resources with their own governance boundaries. This distinction is enough for the introductory audience; resource schemas and setup are intentionally excluded. [R10]

## 3. Capabilities and Customer Fit

### Models and model choice

Foundry Models provides a catalog spanning Microsoft, Azure OpenAI, and other providers, with different model capabilities and deployment options. The catalog supports filtering by characteristics such as region, lifecycle, reasoning, tool calling, and inference task. A catalog listing does not mean every model supports every agent feature, deployment method, or region. Agent Service explicitly refers to **supported** models. [R4] [R5]

Model choice should follow the actual customer task, required capabilities, evaluation results, support expectations, and deployment constraints—not an assumption that one model is best for every workload. Microsoft documents comparing models with real tasks and customer data; model cards expose details, benchmarks, and relevant terms. Model versions also have lifecycles, including deprecation and retirement. [R4] [R8]

Customization can involve instructions, tool connections, application logic, and, for supported models, fine-tuning. These are different kinds of customization: building a custom application or agent does not inherently mean training a new model. Fine-tuning support and deployment paths are model- and feature-specific. [R1] [R4] [R5]

### Custom applications and agents

| Customer need | Foundry capability and important boundary |
|---|---|
| Add AI to an existing application | Consume model capabilities without first building an agent. The team still designs and operates the application experience. [R1] [R4] |
| Configure a managed agent quickly | A **prompt agent** combines instructions, a supported model, and tools. It can be authored in the portal or programmatically; Foundry runs its runtime without customer-maintained agent application code or containers. [R5] |
| Implement specialized agent behavior | A **hosted agent** runs the customer's code/framework on Foundry-managed infrastructure. The customer owns that code; the platform manages surrounding hosting functions such as endpoint, scaling, identity, and session state. [R6] |
| Add actions or retrieve relevant information | Tools include file search, Azure AI Search, code interpreter, custom functions, OpenAPI connections, and MCP servers. Toolboxes can curate reusable tools with centralized authentication and versioning. Individual tool status and networking support must be checked separately. [R5] [R7] [R12] |
| Build real-time spoken experiences | Voice-based prompt agents provide managed voice orchestration, but current documentation explicitly identifies voice-based agents and related capabilities as preview. Do not generalize text-agent publishing behavior to voice channels. [R5] |

### Tooling and visual experiences

Foundry supports portal exploration, model and agent playgrounds, prompt-agent authoring without application code, SDK-based development, and Visual Studio Code workflows. Developers can combine these surfaces—for example, explore in the portal and move into code as requirements grow. The introductory distinction should therefore be **degree of customization and operational control**, not “visual versus nonvisual.” [R1] [R5]

Toolboxes expose curated tools through a managed MCP-compatible endpoint and can also be consumed by compatible runtimes outside Foundry. This provides a concrete example of using a Foundry capability without moving all agent execution onto Foundry. Toolbox availability must not be extended to every tool or to preview skills merely because the toolbox itself is GA. [R3] [R7]

### Illustrative customer use cases

These are capability-grounded examples, not named customer deployments or promised outcomes.

| Illustrative scenario | Why Foundry is relevant | Boundary to preserve |
|---|---|---|
| Employee assistance over approved documents, with selected business actions | Prompt agents can combine instructions, retrieval tools, and action tools; the toolbox documentation uses employee onboarding as an example of coordinating multiple tools. [R5] [R7] | Retrieval and action permissions need deliberate configuration; an agent does not automatically gain access to all company information. [R6] [R7] |
| A customer-facing application needing a tailored assistant or task-specific response behavior | Teams can choose a supported model, test its responses, and embed model/agent capabilities in their own application. [R1] [R4] [R5] | Customer-facing application design, reliability decisions, and use-case testing remain customer responsibilities. [R6] |
| A specialist process requiring custom orchestration or internal service calls | Hosted agents let developers bring custom code and frameworks while Foundry manages the agent hosting environment. [R6] | Custom code and downstream integrations still require maintenance and safety review; hosted does not mean responsibility-free. [R6] |
| A solution team comparing alternatives before production | Evaluation can compare output quality, safety, and task outcomes across models or agent versions using appropriate test data. [R4] [R8] | Evaluation scores are decision evidence, not a guarantee of correct or safe behavior in every future interaction. [R4] [R6] |

## 4. Deployment and Operational Boundaries

**Separate model deployment, agent execution, and user distribution.** Foundry can expose models for applications, run managed prompt agents, or host custom agent code. Publishing an agent into a user-facing channel is a further distribution step; it is not the same operation as selecting a model or deploying the agent runtime. Hosted-agent programmatic endpoints can be available without publishing to Microsoft 365 channels. [R1] [R5] [R6] [R14]

**Managed hosting is not the whole solution.** For hosted agents, Microsoft manages the surrounding runtime infrastructure while the customer owns the agent code and is responsible for use-case testing, responsible AI mitigations, third-party connections, and resulting data flows. Do not imply that hosting the agent also designs or operates every external application, business system, or user interface around it. [R6]

**Versioning and rollout still matter.** Hosted agents use immutable versions; published consumers can use stable endpoints while teams change the active agent version. The current hosted-agent page says an endpoint serves one version at a time and does not support traffic splitting between versions. An introductory description can mention managed endpoints and versioned rollout without promising advanced rollout behavior. [R6] [R14]

**External resources retain separate controls.** Foundry connections do not absorb the networking, access policies, or compliance settings of services such as Azure AI Search and Storage. Likewise, publishing into Microsoft 365/Teams introduces the destination services' data processing, storage, compliance, and residency commitments. Review the end-to-end solution rather than assuming a single platform boundary covers everything. [R10] [R14]

**Foundry is an option, not a universal prerequisite.** Its own documentation accommodates agent code already running elsewhere, and toolboxes can be consumed outside Foundry. The architecture guide also identifies a standalone Azure OpenAI resource as potentially sufficient for a model-only workload. These are concrete counterexamples to a mandatory all-in-one deployment story; they do not establish the architecture of every other Microsoft agent product. [R5] [R7] [R10]

## 5. Evaluation, Observability, Security, and Governance

### Evaluation and observability

Evaluation measures model or agent quality, safety, and reliability. Foundry documents evaluating existing datasets, generating responses from test inputs, evaluating conversations, and evaluating captured production interactions. Evaluators can target outcomes such as relevance, groundedness, task completion, or content safety. The evaluation unit and chosen evaluators must fit the customer's task. [R8] [R9]

Observability combines three complementary activities: **evaluation** scores behavior, **tracing** reveals execution flow such as model and tool calls, and **monitoring** tracks operational and quality signals over time. Microsoft documents OpenTelemetry-based tracing and integration with Azure Monitor Application Insights. These provide evidence for troubleshooting, not an assurance that every internal model reasoning step is exposed. [R9]

Keep the status distinctions visible: core evaluation is listed as GA, but individual evaluators and evaluation features may be preview. Tracing is GA for prompt and hosted agents, while workflow/external-agent tracing and tracing VNet experiences are listed preview. Monitoring is listed preview; do not describe the entire observability stack as uniformly GA. [R3]

### Foundry-specific security and governance

Foundry documents Microsoft Entra identity, Azure RBAC, network isolation, content filtering, and policy capabilities. Access can be scoped at resource and project levels. The GA overview recommends Entra ID with RBAC for governance-sensitive workloads and notes that agents and evaluations require Entra authentication. These are platform-specific controls, not evidence that every Microsoft AI product has identical security behavior. [R1] [R3] [R10]

Guardrails define detected risks, scanning points, and response actions. **Model guardrails and agent guardrails have different status and applicability:** model guardrails are listed GA, while agent guardrails and tool-call/tool-response intervention points are preview. Current guardrail documentation says agent guardrails apply to agents developed in Foundry Agent Service, not automatically to other agents registered in Foundry Control Plane. Registration therefore does not prove equivalent protection. [R3] [R11]

Network isolation requires feature- and tool-specific review. Some tools can use private paths; others use public endpoints even with a network-isolated Foundry resource. For example, the networking documentation lists web search and SharePoint grounding as public-endpoint tools. Avoid saying “all data and tool traffic stays inside the customer's private network.” [R12]

The named Foundry Control Plane offers fleet inventory, observability, compliance, and security views. It is documented as preview, and its Operate panes are listed preview in the readiness table. Present it as a documented management capability with those qualifications—not as proof that all fleet governance functions are generally available or automatically enforced across every platform. [R2] [R3] [R13]

### Regional availability and operational capacity

Project availability does not establish that a desired model, Agent Service feature, evaluation capability, or tool is available in that location. Microsoft's region article explicitly says it is not a real-time matrix for every model/feature combination and requires service-specific checks and quota validation. Sovereign-cloud feature parity must not be assumed. No “available everywhere” claim is supported. [R18]

Before a real deployment decision, validate the required model, feature, region, quota/capacity, network configuration, and connected services together. This research intentionally avoids numeric quotas and region lists because there is no specified customer location or production workload, and such lists would not establish workload eligibility. [R10] [R18]

## 8. Research Limitations and Owner Handoff

### Evidence limits and documentation inconsistencies

1. **Documentation verification, not a deployed test.** Microsoft Learn search and full-document fetch succeeded; all 18 references were fetched through Learn. Known Learn URLs were also read as HTML solely to obtain date metadata. No tenant, portal, model, quota, network, publishing, or integration behavior was tested.
2. **Classic/current material can be mixed.** The models overview retains classic/hub-specific managed-compute guidance, while the newer readiness table describes managed compute as a preview deployment type. The report therefore does not prescribe a managed-compute setup or claim all catalog models are deployable through the same current-portal path. For platform naming and portal boundaries it relies on the explicit migration and readiness guidance. [R2] [R3] [R4]
3. **Activity-endpoint instructions are not fully synchronized.** The Copilot Studio standard-harness article says Activity enablement is programmatic only; the newer Foundry publishing article says portal publishing enables the Activity protocol. For publishing behavior, the newer, operation-specific Foundry instructions are preferred. The supported cross-product claim here is deliberately narrower: the connection requires an enabled Activity endpoint; no universal “code-only enablement” claim is made. Detailed connection procedure needs reconciliation before implementation. [R14] [R15]
4. **Preview scope matters more than broad capability prose.** Overview pages describe broad observability and governance capabilities. For status, this report uses the explicit readiness table, migration feature comparison, and feature-level preview warnings rather than assuming an unqualified overview implies GA. [R2] [R3] [R5] [R11]
5. **No historical announcement timeline is asserted.** The evidence establishes current naming and current documented statuses as retrieved on 2026-10-30. Source metadata does not establish the original announcement or launch date. No cited source was inaccessible, and no announcement-only capability is promoted to a shipping claim.
6. **Intentional exclusions.** No APIs, commands, SDK setup, deep architecture, licensing/pricing matrix, model inventory counts, benchmarks, customer ROI claims, slides, or content draft are included. Code-sample search was not needed because no substantive code or commands are provided.

### Cross-owner handoff

Relevant retrieved pages contain IQ references, but their labels are not reproduced as substantive findings here; the owner must independently reconcile its evidence. - **github-copilot — development versus hosting:** The supported connection here is coding assistance via Foundry Skill, not a transfer of runtime ownership to GitHub Copilot. Coordinate current tool naming and any host-specific status before broader use. [R6] [R16]
- **All owners — dated status caveat:** Do not use preview declarative workflows as an unqualified current recommendation. The documented retirement is December 1, 2026, while portal-based prompt-agent authoring remains a separate capability; neither “Foundry is code-only” nor “the visual workflow designer is a durable new-development path” is supported.
